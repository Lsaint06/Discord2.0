# Discord 2.0 v1.4.0 — deployment and rollback plan

**Status: plan only.** Nothing in this document has been run on the Jetson. Each stage needs your
explicit go-ahead, and you can stop safely after any of them. It builds on the conventions of
[milestone-11-project-connect.md](milestone-11-project-connect.md#backup-and-rollback) and was
rehearsed on this PC with production-era data (see the
[release-readiness report](v1.4.0-release-readiness.md), sections B and C). Compatibility details
are in [v1.4.0-compatibility.md](v1.4.0-compatibility.md).

## What changes and what doesn't

| Part | v1.4.0 change |
| --- | --- |
| Server code | Milestones 13 + 14 (`86831b4` → the release commit) |
| Database | 7 **additive** migrations (6–12) applied automatically at the first start, each in its own transaction. New tables: `email_codes`, `server_icons`, `upload_sessions`, `server_timeout_holds`, `soundboard_sounds`, `saved_messages`, `user_notes`; new columns; 2 new triggers. Nothing is dropped or rewritten. |
| Dependencies | +1: `nodemailer` (pure JavaScript, only used when email is configured) |
| `docker-compose.yml` | Passes the optional Milestone 13 settings through to the server, all defaulting to **off**. No new services, ports or volumes. |
| `Dockerfile`, Caddyfile, LiveKit config | Unchanged |
| `.env` on the Jetson | **No change needed** |
| DNS, DuckDNS, router port forwards | **No change** |
| Behaviour changes for people | Owner/Administrator/Moderator gain "Moderate Members" (timeouts) by default. Unread tracking treats never-opened channels as read up to their start. Email, open registration, GIFs and large files stay off. |

**Downtime:** a short stop for the preparation backup (about 10 seconds for a small volume; longer if
the attachments are large), then 1–2 minutes for the switch. Only the
`server` container is recreated: LiveKit and Caddy keep running. Ask people to leave voice calls
first, because the backend restart can drop them.

## Stage 1 — prepare (production keeps running, apart from the short backup stop)

1. **Keep today's image for rollback.** The running container must use exactly this image:
   ```bash
   cd ~/Discord2.0/server
   sudo docker inspect -f '{{.Image}}' "$(sudo docker compose ps -q server)"
   sudo docker image inspect -f '{{.Id}}' discord2-server:dev       # same ID as above
   sudo docker tag discord2-server:dev discord2-server:m11-rollback
   ```
2. **Consistent backup.** The server is stopped, so `discord2.db`, `-wal` and `-shm` match:
   ```bash
   B=~/discord2-backups; TS=$(date +%Y%m%d-%H%M%S); D="$B/v140-prep-$TS"; install -d -m 700 "$D"
   git rev-parse HEAD > "$D/commit.txt"; sudo docker compose --profile public images > "$D/images.txt"
   install -m 600 .env "$D/env.pre-v140"
   sudo docker compose stop server
   sudo tar -C /var/lib/docker/volumes/server_discord2-data/_data -czf "$D/data.tgz" .
   sudo docker compose start server
   sudo chown "$USER" "$D/data.tgz" && chmod 600 "$D/data.tgz"
   sha256sum "$D/data.tgz" > "$D/data.tgz.sha256"
   ```
3. **Verify the backup** with today's image, without network access:
   ```bash
   V=$(mktemp -d); sudo tar -xzf "$D/data.tgz" -C "$V"
   d2cli() { sudo docker run --rm --network none --user 0:0 -v "$V":/v -e NODE_ENV=production \
     -e DEV_AUTH=false -e DATABASE_URL=sqlite:/v/discord2.db "$@"; }
   d2cli discord2-server:m11-rollback node dist/cli/admin.js verify | tee "$D/verify-before.txt"
   # must end with "OK: no integrity problems found."
   echo "attachment files: backup $(sudo find "$V/attachments" -type f | wc -l), live $(sudo find /var/lib/docker/volumes/server_discord2-data/_data/attachments -type f | wc -l)"
   ```
4. **Build the v1.4.0 image** from a separate checkout, so the running folder stays untouched:
   ```bash
   cd ~/Discord2.0 && git worktree add --detach ~/d2-v140 "$REL"
   sudo docker build --progress=plain -t discord2-server:1.4.0-rc1 ~/d2-v140/server 2>&1 | tee "$D/build.log"
   grep -E "sharp [0-9]" "$D/build.log"         # sharp + libvips loaded on ARM64 (the Dockerfile checks it)
   sudo docker image inspect -f '{{.Id}} {{.Architecture}}' discord2-server:1.4.0-rc1   # ... arm64
   ```
5. **Rehearse the upgrade on the copy of the real data** (still `$V` from step 3; no network):
   ```bash
   d2cli discord2-server:1.4.0-rc1 node dist/cli/admin.js verify | tee "$D/verify-after.txt"
   # applies migrations 6-12 to the COPY; must end with "OK"; foreignKeyViolations 0
   d2cli discord2-server:m11-rollback node dist/cli/admin.js verify | tee "$D/verify-rollback.txt"
   # the OLD server still opens the migrated copy (that is what rollback R1 relies on)
   ```
   Compare the three outputs. Users, accounts, messages, attachments, reactions, pins and memberships
   must be identical, with no orphans.
6. **Optional: staging run** of the new server on the copy, reachable only from the Jetson itself.
   It has no LiveKit, mail or GIF settings, so it makes no outbound calls:
   ```bash
   sudo docker run -d --name d2-staging --user 0:0 -p 127.0.0.1:3901:3001 -v "$V":/data -e DEV_AUTH=false discord2-server:1.4.0-rc1
   sleep 8; curl -s http://127.0.0.1:3901/health; echo; curl -s http://127.0.0.1:3901/api/meta; echo   # apiVersion 6, voice false
   sudo docker logs d2-staging 2>&1 | grep -iE "error|warn" | head
   sudo docker rm -f d2-staging
   ```
7. Clean up the scratch copy: `sudo rm -rf "$V"`.

**Stop here if** the image doesn't build, `verify` fails on the copy, or the counts differ. Production
is unchanged (rollback R0: nothing to undo).

## Stage 2 — deploy (1–2 min outage)

1. Tell people; ask them to leave voice calls.
2. **Pre-deploy backup.** This is the one rollback R3 would restore. The server stays stopped
   from here until the new one starts:
   ```bash
   cd ~/Discord2.0/server
   B=~/discord2-backups; TS=$(date +%Y%m%d-%H%M%S); P="$B/v140-deploy-$TS"; install -d -m 700 "$P"
   git rev-parse HEAD > "$P/commit.txt"; install -m 600 .env "$P/env.pre-v140"
   sudo docker compose stop server
   sudo tar -C /var/lib/docker/volumes/server_discord2-data/_data -czf "$P/data.tgz" .
   sudo chown "$USER" "$P/data.tgz" && chmod 600 "$P/data.tgz"
   tar -tzf "$P/data.tgz" > /dev/null && sha256sum "$P/data.tgz" > "$P/data.tgz.sha256" && echo backup-ok
   ```
3. **Switch the code and image.** `.env` stays as it is:
   ```bash
   git checkout --detach "$REL"                         # new docker-compose.yml (optional settings, default off)
   sudo docker compose --profile public config --quiet && echo compose-ok
   sudo docker tag discord2-server:1.4.0-rc1 discord2-server:dev
   sudo docker compose --profile public up -d --no-build --pull never server
   ```
4. **Confirm it started on the new image:**
   ```bash
   sudo docker inspect -f '{{.Image}}' "$(sudo docker compose ps -q server)"   # = ID of discord2-server:1.4.0-rc1
   sudo docker compose --profile public ps        # server (healthy); livekit and caddy NOT recreated
   sudo docker compose logs --since 5m server | grep -iE "error|warn|listening"
   sudo docker compose exec -T server node dist/cli/admin.js verify            # OK
   ```

**Acceptance tests** — the release decision depends on these. Use at least:

- PC A at home with v1.4.0-rc.1;
- PC B **outside** the home network (for example on a phone hotspot) with v1.4.0-rc.1;
- one PC still on **1.2.0**.

Three people make the voice and soundboard checks meaningful.

- [ ] **1.2.0 app:** sign in, history, send text and an image, DMs, join and leave voice. Same as before.
- [ ] **Sign-in and sync (rc.1):** a theme picked on PC A appears on PC B. A theme picked earlier on the
      old server moves to the account once.
- [ ] **Profile Studio:** save a gradient, decoration, effect and name style; the other PC sees them.
      Upload an **animated** GIF avatar and banner while watching `tegrastats` on the Jetson. Note the
      peak CPU and how long the upload takes (it must finish well under the 60 s limit).
- [ ] **Saved messages and notes:** they sync between your own PCs; another account can't see them.
- [ ] **Voice:** 2–3 people join, hear each other, mute/deafen and leave.
  - Your own icon disappears **at once** for you when you leave. On the other PCs it should go within
    about a second.
  - Rejoin works.
- [ ] **Soundboard:**
  - a manager uploads a clip; someone in the call plays it;
  - everyone **in that channel** on 1.4.0 hears it, people outside don't;
  - the 1.2.0 PC hears nothing (expected);
  - a fast burst hits the rate limit.
- [ ] **In-call sounds:** push-to-talk on/off and screen-share start/stop sounds. Turn Wi-Fi off for
      20 s: the connection-lost and reconnected sounds play, and chat and voice recover by themselves.
- [ ] **Screen share** 1440p60 from B to A and back: the stream stats look like they did on 1.2.0.
- [ ] **Moderation:** a moderator times out a member, the member can't send, and the timeout ends on time.
- [ ] **Restart:** `sudo docker compose restart server`. Every app reconnects without duplicate
      messages or members.
- [ ] **PC CPU during a call** with an animated theme (Aurora) in Task Manager. If it's high,
      "Reduced" theme effects bring it down.

## Rollback (decision points; nothing runs automatically)

| Situation | Action |
| --- | --- |
| Stage 1 fails (build, verify on the copy) | **R0**: nothing to undo. Production never changed. Remove the worktree when done. |
| Stage 2 fails before the new server has started | **R0**: `git checkout milestone-11-connect`, `sudo docker tag discord2-server:m11-rollback discord2-server:dev`, `sudo docker compose --profile public up -d --no-build --pull never server` |
| New server running, but something is wrong (default) | **R1**: old image on the migrated database; all data kept |
| Security problem | **R2**: close the router forwards first, then R1 |
| Database damaged (`verify` or the integrity check fails) | **R3**: restore the pre-deploy backup; writes since then are lost |

**R1 — old server on the migrated database.** Rehearsed: `verify` OK and 20/20 write operations, then
roll-forward again with 20/20.

```bash
cd ~/Discord2.0/server
sudo docker compose stop server
git checkout milestone-11-connect && git rev-parse --short HEAD     # 86831b4
sudo docker tag discord2-server:m11-rollback discord2-server:dev
sudo docker compose --profile public up -d --no-build --pull never server
sudo docker inspect -f '{{.Image}}' "$(sudo docker compose ps -q server)"   # = m11-rollback ID
sudo docker compose exec -T server node dist/cli/admin.js verify            # OK
curl -s https://landhoev3.duckdns.org/api/meta; echo                        # "apiVersion":4
```

The database keeps migrations 6–12, which the old server ignores.

- New-feature data (profile styles, synced themes, soundboard clips, saved messages, notes, timeouts)
  stays stored but is unused until you roll forward. To roll forward, repeat Stage 2 step 3.
- 1.2.0 apps work as before; 1.4.0 apps fall back as described in the compatibility document.

**R2 — close exposure first.** Remove the router forwards (80, 443, 7881/tcp, 7882/udp), or
`sudo docker compose --profile public stop caddy`, then decide between R1 and R3.

**R3 — damaged database only.** Restore the backup taken **immediately before** the deployment, never
an older one. Rehearsed: 0 differences in 3,856 checked values.

```bash
sudo docker compose stop server
sudo tar -C /var/lib/docker/volumes/server_discord2-data/_data -czf ~/discord2-backups/damaged-$(date +%Y%m%d-%H%M%S).tgz .
sha256sum -c "$P/data.tgz.sha256"
sudo find /var/lib/docker/volumes/server_discord2-data/_data -mindepth 1 -delete
sudo tar -xzf "$P/data.tgz" -C /var/lib/docker/volumes/server_discord2-data/_data
# then R1 (old image) or start 1.4.0 again, as decided
```

**Failure notes:**

- A migration that fails rolls back its own transaction. The database stays at the previous version,
  so R1 is safe.
- If the new container keeps restarting, `sudo docker compose logs server` shows why. Don't retry in
  a loop; use R1.

1. Set the final version and build the production configuration (the Internet and Home servers come
   from `desktop/.env.production`):
   ```powershell
   cd desktop
   npm version 1.4.0 --no-git-tag-version
   npx electron-vite build
   npx electron-builder --win nsis zip --publish never --config.directories.output=dist/v1.4.0
   Get-FileHash dist\v1.4.0\*.exe, dist\v1.4.0\*.zip -Algorithm SHA256
   ```
2. **Code signing.** Smart App Control blocked both unsigned rc.1 executables on this PC. Friends with
   Smart App Control on will likely be blocked too. Options are in
   [milestone-11-project-connect.md](milestone-11-project-connect.md): build and sign in CI, and
   publish the SHA-256 next to each file. Never ask friends to turn Smart App Control off.
3. Share the files privately with their hashes. 1.2.0 keeps working, so people can update at their
   own pace (see the compatibility document for what they miss).

**Release notes for friends:**

- **New:**
  - 12 themes;
  - Profile Studio (gradients, decorations, effects, name styles), animated avatars and banners;
  - 6 sound packs and the soundboard (everyone in the call needs 1.4.0 to hear it);
