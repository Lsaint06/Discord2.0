## Verdict: NOT READY for release

v1.4.0 is **prepared, but not releasable yet**. Everything that can be proven on this PC passed:

- the migration and rollback rehearsals on production-era data;
- compatibility in both directions;
- the security and performance audit (two problems found and fixed);
- all automated gates;
- a versioned release-candidate build.

What decides a release can only be tested against the upgraded backend on the Jetson, and has
**not** been tested:

- real voice calls through LiveKit on the new server;
- soundboard clips heard by other people;
- several PCs at once, including one outside the home network;
- the Docker image build and the migration on a copy of the **real** database on the Jetson (ARM64).

Two distribution risks remain:

- The rc.1 executables are unsigned, and **Smart App Control blocked both on this PC**. Friends may
  see the same.
- Nobody has measured animated-image processing on the Jetson's CPU.

**Recommended path.** Each step needs your explicit approval:

1. Commit the release-prep changes.
2. Run Stage 1 of the [deployment plan](v1.4.0-deployment-and-rollback.md): backup, image build and
   a migration rehearsal on a copy of the real database. Production only stops for the backup.
3. Deploy in a quiet hour (Stage 2).
4. Run the acceptance tests (Stage 3) with at least two PCs, one of them remote.

Call v1.4.0 released only when Stage 3 passes.

## Smart App Control

Both rc.1 executables were refused at launch:

- `Start-Process` failed with: "This command cannot be run due to the error: An Application Control
  policy has blocked this file."
- Code Integrity logged event **3077**, policy **`VerifiedAndReputableDesktop`**
  `{0283ac0f-fff1-49ae-ada1-8a933130cad6}` (requested signing level 2, validated 1).
- `HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy\VerifiedAndReputablePolicyState` = 1 (enforcing).

They were **not bypassed**: the files were not unblocked, renamed, re-signed or started another way.
The policy itself was not changed.

To test the payload, A7 ran each build's `app.asar` on the project's development Electron binary
(`desktop\node_modules\electron\dist\electron.exe`, 44.9.3). That is the same runtime `npm run dev`
uses. It isn't Authenticode-signed either; Smart App Control allows it, presumably on reputation.
The packaged `Discord2.exe` is that binary renamed, with our icon and version resources added.
That makes it a new, unknown file for every build.

The installed 1.2.0 was allowed, the m14.3 preview was blocked and the voice-fix build was allowed.
The outcome is unpredictable, so **code signing** is the real fix (see
[milestone-11-project-connect.md](milestone-11-project-connect.md)).

## Fixes made during this audit

1. **Soundboard orphaned-file sweep** (server, E5).
   - `cleanupSoundboard()` in `server/src/routes/soundboard.ts` now runs in the hourly clean-up
     chain in `server/src/app.ts`.
   - It only deletes files in `attachments/soundboard/` that match `^[a-f0-9]{32}\.wav$`, have no
     database row and are older than 1 hour, so uploads in progress are never touched.
   - New test: "orphaned clip files" in `server/test/soundboard.test.ts`.

   - `.settings-content-inner` got `min-width: 0` in `desktop/src/renderer/src/assets/main.css`.
   - Wide content such as the theme gallery now wraps instead of widening the page.
   - Re-checked: 24/24 settings sections at 100% and 150% are clean (`ev/25`).
