**Built-in safety checks in `stg.sh`** (tested by `stg-guards.sh`, 131 checks):

1. **Production fingerprint.** `baseline` records each production container's ID, image, start
   time and restart count, plus the `:dev` image ID and the production volume. Every step that
   changes something re-checks it and **stops** on any difference.
2. **Allowed images.** Only the two staging images; `:dev` is refused.
3. **Destructive steps** (`restore`, `teardown`) only act on `d2staging_staging-data` when:
   - its Compose labels say `d2staging / staging-data`;
   - no container from another project uses it;
   - you type the exact name.

   They never run `down -v`.
4. **Tools** only talk to `http://server:3001`, the staging service name inside the staging network.
   Production's 3001, the LAN address and the public hostname are refused.
5. **Seeding** refuses a server that already has accounts (other than the system bot).

**What staging shares with production:** the Jetson's CPU, memory, disk and LAN.

- The image build and a 1440p60 test stream are heavy.
- Run staging in a quiet hour, with nobody in a production call.

## Two PCs on the home LAN: why it works

| Path | Address | Checked by |
| --- | --- | --- |
| App → staging API and gateway | `http://` and `ws://192.168.68.65:3901` | Staging client build: CSP `http://192.168.68.65:* ws://192.168.68.65:*`, one compiled server, download origin `http://192.168.68.65:3901` (`ev/35`) |
| App → LiveKit signaling | `ws://192.168.68.65:7980`, handed out by the server | Server test: production-mode config accepts it (plain `ws://` only because the address is private) and returns it for LAN clients. App test: the voice-address check accepts it and refuses public or foreign hosts |
| Media (ICE) | Host candidates `192.168.68.65:7982/udp`, and `:7981/tcp` as fallback | `use_external_ip: false`, `node_ip` = LAN address, candidates restricted to `<LAN IP>/32`, so no Docker bridge or public candidates and no STUN lookup. Both PCs reach the Jetson directly on the same LAN; no TURN needed. The client PCs only make outbound connections, so Windows Firewall needs no rule |
| Backend → LiveKit API | `http://host.docker.internal:7980` | Same mechanism as production (7880) |
| LiveKit → backend webhooks | `http://192.168.68.65:3901/api/livekit/webhook`, signed with the staging key | Validator. This is what removes your icon from the voice list for others when you leave |

**Never public:**

- The router forwards only 80, 443, 7881/tcp and 7882/udp to production. None of 3901 or 7980–7982
  is forwarded.
- Like production's, the staging LiveKit listens on all of the Jetson's interfaces. Preflight checks
  every IPv6 address Linux labels `scope global`:
  - **Unique-local** (`fc00::/7`, for example `fd7c:…`) and **link-local** (`fe80::/10`)
    addresses pass. Linux calls unique-local addresses "global", but the internet can't route
    to them. They are LAN-only like `192.168.x.x`, so the other PC can use them and nothing
    outside can.
  - **Global unicast** (`2000::/3`), and anything it can't recognise or parse, gives a **WARN**
    listing those addresses. In that case, check that the router blocks inbound IPv6 to 3901 and
    7980–7982 before starting (or add the LAN-only `ufw` rules below).
- If `ufw` is active, preflight says so. The rules needed are LAN-only:
  ```bash
  sudo ufw allow from 192.168.68.0/22 to any port 3901,7980,7981 proto tcp
  sudo ufw allow from 192.168.68.0/22 to any port 7982 proto udp
  ```
  Milestone 11 found no host firewall.

## Representativeness of the migration rehearsal

**The same as the real upgrade:**

- **Production's exact server image.** `m11-rollback` must have `:dev`'s ID, and `build` checks
  this.
- **Same host, architecture, Docker engine and LiveKit image.**
- **Data created through production's own API** (API 4) by the old code, which also creates the
  owner with its admin CLI.
- **Same upgrade path:** migrations 6–12 run at the first start of the new image.
- **Same backup method:** server stopped, tar of the whole data directory (database, WAL and
  attachments), verified by the old image's `admin verify` on a scratch copy without network access.
- **Same rollback:**
  - R1: the old image on the migrated database;
  - roll forward;
  - R3: restore the pre-upgrade backup.

**Differences, and why they're acceptable:**

- **Smaller, synthetic data:** 6 accounts, 1 extra server, about 40 messages, 3 attachments.
  - Production's real content shapes are covered offline on deployment day (B5).
  - Development-era legacy identities were covered by the local rehearsal.
- **The backup reads the volume through a throw-away container** instead of the host path. It is
  the same tar of the same directory.
- **No Caddy and `ws://` instead of `wss://`,** so the internet path isn't exercised. It is
  unchanged in this release and is checked in deployment Stage 3.
- **Staging has CPU and memory limits** that production doesn't, so its performance numbers are
  slightly pessimistic.

## Remaining risks

| Risk | Severity | Mitigation |
| --- | --- | --- |
| The image build or a 1440p60 stream slows production during the test | Medium | Quiet hour; staging capped at 2 CPUs and 1 GB per container; `check-production` after each step |
| Inbound IPv6 reaches staging's LiveKit ports if the Jetson has a global unicast (`2000::/3`) IPv6 address and the router allows it | Medium | Preflight warns for such addresses (not for unique-local `fd…`, which the internet can't route); check the router before G4, or add the LAN-only `ufw` rules |
| The second PC blocks the unsigned staging exe | Medium | Run it from a source checkout, or use a PC without Smart App Control. Real fix: code signing |
| Synthetic data doesn't reproduce every real-data shape | Medium | Offline verify on a copy of the real backup in deployment Stage 1 (B5) |
| `discord2-server:m11-rollback` and `:1.4.0-rc1` stay on disk (about 1–2 GB) | Low | Needed for the deployment; removal commands in G9 |
| LiveKit's UDP buffer warning (as in production) | Low | Unchanged from production; tuning `rmem_max` is a separate decision |
| `stg.sh` has only been exercised with a fake docker and Git Bash on Windows, not on the Jetson | Low | Every step stops at the first error; `preflight` and `config` are read-only and run first |
